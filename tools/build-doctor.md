# build-doctor

Компактная диагностика проваленных сборок. Использует парсер задач и поиск
журналов buildapi, работает без запущенного HTTP-сервера и без API-ключа.
Требования: Python 3.10+ и `ercat` для сжатых журналов.

```sh
./tools/build-doctor triage
./tools/build-doctor triage --product WINE --version 10-testing
./tools/build-doctor triage --dist RedOS/7.3 --json
./tools/build-doctor diagnose TASKID
./tools/build-doctor diagnose TASKID --component wine32-etersoft-grdwine
./tools/build-doctor diagnose TASKID --verbose --limit 10 --json
```

`TASKID` — имя файла задачи без `.task.failed`; это расширение также принимается.
Каталог задач задаётся `--sales-dir` или переменной `SALES_DIR`, по умолчанию
`~/sales`. Фильтры системы и продукта ищут подстроку, версия сравнивается точно.

`triage` группирует текущие провалы по продукту, системе, версии и компоненту,
сортирует по числу задач. Используется последняя ошибка каждой задачи.
Один компонент учитывается один раз на задачу, даже если провалились и установка
зависимостей, и сборка. Неопознанные ошибки попадают в `unknown`.
`--verbose` показывает все идентификаторы задач группы. `sales-tasks errors`
использует этот же разбор; формат его вывода теперь совпадает с `triage`.

`diagnose` ищет журналы в стандартных каталогах артефактов через buildapi.
Для `wine32-*` учитывает журналы `wine-*` 32-битного окружения.
По умолчанию выводит до трёх журналов, до десяти строк контекста каждого;
`--verbose` увеличивает контекст до тридцати строк. В первую очередь выбирается
журнал системной задачи, затем журналы сборок, затем установки зависимостей.
Из подробного журнала выделяется последний этап `STEP ... [FAILED]`.
Если известного сообщения об ошибке нет, выводится контекст с явной пометкой.

Дата провала разбирается из сообщения робота на русском или английском языке
(MSK/UTC), дата журнала берётся из его `mtime`. В JSON `time_relation` принимает
`older`, `newer`, `near_attempt` (разница не более пяти минут) или `unknown`.
Близость времени сама по себе не доказывает принадлежность журнала попытке.
Дата изменения файла задачи не используется вместо даты провала.
Общие журналы могут быть перезаписаны последующими сборками.

Чтение сжатого журнала ограничено 20 секундами и 64 МиБ распакованных данных;
анализируется хвост размером до 256 КиБ. При превышении лимита выводится ошибка
чтения, а неполный фрагмент не выдаётся за конец журнала.

Диагностические команды только читают данные. Они не запускают сборки,
не перезапускают задачи и не записывают комментарии проверки; отдельная
явная команда `review` записывает комментарии (см. ниже). Результат `diagnose` — материал для
проверки оператором; после проверки комментарий записывается штатным механизмом
buildapi согласно AGENTS.md.

Проверки:

```sh
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s tests -p test_build_doctor.py
bash -n tools/sales-tasks
```

## Проверка зависимостей

```sh
./tools/build-doctor deps TASKID
./tools/build-doctor deps TASKID --component wine-etersoft --json
./tools/build-doctor deps TASKID --query --module wine-10.0
```

`deps` находит `.rpm.depends` в Sisyphus рядом с деревом журналов продукта,
для выбранного пакета (подпакеты не объединяются автоматически). Выводит отсутствующие имена из журналов и их
текущее преобразование. Использует штатные функции Korinf `parse_dist_name`,
`set_target_var`, `print_pkgrepl_list`, `tolocal_anyrepl`, включая наследование
и scripted rules. `--verbose` и JSON показывают все преобразования и пути
файлов правил с разрешёнными симлинками. Ошибки чтения и несовпадение времени
журнала доступны в выводе. Имена из старого журнала не являются результатом
новой проверки установки.

Без `--query` контейнер не запускается. `--query` выполняет `epm search`
через `korexec`, требует явного `--module` и доступа к сборочным окружениям.
Поиск удаляет завершающие цифры версии ABI из имени; кандидаты требуют
проверки совместимости и автоматически не подставляются. Поиск может
обновлять кеш пакетного менеджера временного окружения.

## Статус задач и комментарии проверки

```sh
./tools/build-doctor status TASKID1 TASKID2 TASKID3 TASKID4
./tools/build-doctor status --dist x86_64/RedOS/7.3 --version 10.10 --json
./tools/build-doctor status --product WINE@Etersoft --done-dir ~/done
./tools/build-doctor review --dist x86_64/RedOS/7.3 --version 10.10 \
    --text-file /tmp/report.txt --log /path/to/wine-etersoft.log.xz --dry-run
./tools/build-doctor review TASKID --text-file /tmp/report.txt \
    --log /path/to/wine-etersoft.log.xz --replace
```

`status` показывает очередь и завершённые задания из `~/done` (настраивается
`--done-dir`/`DONE_DIR`). Для явно указанных ID возраст завершённой задачи
не ограничен; при фильтрах учитываются последние 48 часов архива и вся очередь.
Фильтры `--dist`, `--version`, `--product` сравниваются точно; IDs и фильтры
не смешиваются. Вывод содержит статус, последнее сообщение провала и `done_at`,
без полей клиента; известные имена и адреса из сообщения ошибки скрываются.
Если задача снова есть в очереди, её состояние приоритетнее старого `.done`.

`review` записывает комментарий через `buildapi.comments.write`, не меняя очередь.
Выберите IDs или оба точных фильтра `--dist` и `--version`. По фильтрам выбираются
только текущие failed; явно указанный ID другого статуса вызывает ошибку.
Файл текста должен содержать проблему и способ решения отдельными абзацами.
Пустой ввод запрещён и никогда не удаляет комментарий.

`--log` обязателен: укажите именно изученный журнал. Проверяются его наличие
и принадлежность журналам продукта/версии/целевой системы задачи через штатный
поиск buildapi; симлинки разрешаются. `log_at` берётся из mtime журнала,
`updated_at` — фактическое время записи. Несовпадение времени журнала с попыткой
показывается в результате; оно требует осмысленного объяснения в тексте.
Существующий комментарий обновляется только с `--replace`. `--dry-run` проводит
те же проверки и выводит выбранные IDs и действия без записи.
Весь набор проверяется до первой записи, а состояния задач перепроверяются
непосредственно перед записью. Это не транзакция с роботом: файловые ошибки
во время записи могут оставить часть комментариев уже записанной.

### Видимость проверок

`status` для failed показывает `Review: <дата>` или `missing`/`unreadable`.
`triage` показывает по каждой группе число комментариев, число отсутствующих
и нечитаемых записей, число проверок до последнего провала и дату самой
последней проверки группы. Эта дата не означает, что вся группа проверена.
JSON содержит объект `review` в статусе задачи, агрегат `review` группы
и словарь `reviews` по ID в triage. Текст комментариев не выводится.

`before_latest_failure` сравнивает `updated_at` комментария с датой последнего
провала, только если дата надёжно разобрана. При неизвестной дате — `null`.
Сам возраст записи не считается признаком проблемы. Нечитаемые JSON или
некорректные метаданные помечаются `unreadable`, а не отсутствующими.
Показ сводки не изменяет комментарии, их текст и время проверки.
